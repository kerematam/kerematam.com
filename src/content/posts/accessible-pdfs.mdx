By **Kerem Atam**, HelioCampus

> [!NOTE] About this post
> At HelioCampus we build and maintain [Typfolio](https://github.com/HelioCampus/typfolio), an open-source library that turns Typst templates and data into PDFs in the browser. Accessibility has been part of it from the start: every PDF is tagged by default, PDF/UA is a compile option, and the dev tools warn about tables without headers.
>
> Our latest release goes further into tables: telling a screen reader which row and column each cell belongs to. While working on it we measured something that matters to anyone who generates PDFs: **a table can be close to useless with a screen reader and still pass PDF/UA validation.** The first half of this post shows that, for any tool. The second half shows the fix in Typfolio.

## Three tables, one verdict

Here is a small table, as it looks on the page.

<TableTags label="A table with the columns Student, Autumn and Spring, and two rows: Ada with 9 and 8, Ben with 7 and 6." />

We generated it as a PDF three ways, and did two things with each file. We ran it through [veraPDF](https://verapdf.org), the validator most teams put in CI, against PDF/UA-1. And we listened to it with three screen readers, moving down the "Autumn" column to the cell "9": VoiceOver in Preview on a Mac, and NVDA and JAWS in Adobe Acrobat Reader on Windows.

| How the table was written | VoiceOver | NVDA | JAWS | veraPDF, PDF/UA-1 |
| --- | --- | --- | --- | --- |
| A bold first row, no header cells | "9" | "row 2, 9" | "9, Row 2 of 3" | Passes |
| A header row | "9" | "row 2, 9" | "9, Row 2 of 3" | Passes |
| A header row, and a header for each row | "Ada 9" | "Ada, row 2, 9" | "Ada, 9, Row 2 of 3" | Passes |

All three pass, with no failed rule (veraPDF 1.30). But go down the column in the first two and every screen reader gives you a number and, at best, its position. Only the third says whose score it is, and all three screen readers say it.

Hear it for yourself, in VoiceOver's words. Pick a version, go down the "Autumn" column, then switch version and do it again.

<TableListen />

**If a validator is your accessibility test, it is not catching this.** It is not a flaw in the validator. A validator checks that the tags in the file are well formed. It cannot know that "Ada" names a row, any more than an HTML validator can know that a `<td>` should have been a `<th scope="row">`. The file is valid. The table is still hard to use.

## The viewer matters as much as the file

A screen reader does not read the PDF. It reads what the app showing the PDF passes on, and apps differ a great deal. We opened the same three files in five viewers.

| Viewer | Screen reader | Read as a table? | Row header spoken? |
| --- | --- | --- | --- |
| Adobe Acrobat Reader | NVDA, JAWS | Yes | Yes |
| Firefox | NVDA, JAWS | Yes | Yes |
| Preview, Safari | VoiceOver | Yes | Yes |
| Firefox | VoiceOver | No: VoiceOver finds no table | No |
| Chrome | NVDA, VoiceOver | No: lines of text, such as "Ada 9 8", or nothing | No |

So good tags are necessary and not sufficient. Without row headers in the file, no viewer can announce them. With them, the viewers that read the tags do. Test with the viewer and screen reader your readers use, not only the ones on your desk.

Tested in November 2026 with Acrobat Reader 26.2, Firefox 160, Chrome 157, NVDA 2026.2 and JAWS 2026 on Windows 11, and VoiceOver on macOS 26.

## What a screen reader needs from a table

A sighted reader finds a value by running an eye along a row and up a column. A listener cannot. When they land on a cell, the screen reader has to say where they are, and it can only use what the tags say. If you have built an accessible HTML table, you already know the three ingredients. A tagged PDF has the same three.

### 1. Header cells are marked as headers

In HTML, `<th>` and `<td>`. In a PDF, the tags TH and TD. A row that only looks like a header, because it is bold, is tagged as data: that is the first row of the results above.

  legend={[

/>

### 2. Each header says what it labels

In HTML, `scope="col"` and `scope="row"`. In a PDF, a Scope on the TH. Without it, "Ada" is a header, but nothing says it labels the cells beside it and not the cells below it.

<TableTags
  marks={headers}
  scope
  legend={[
    { kind: "col", text: "scope Column: labels the cells below it" },
    { kind: "row", text: "scope Row: labels the cells beside it" },
  ]}
  lines={tree(headers)}
  label="The same table. A dotted arrow runs down from each column header over its column, and across from each row header over its row."
  caption="Each dotted arrow covers the cells a header labels. Column headers point down, row headers point across."
/>

### 3. Each cell is tied to its headers

In HTML, the `headers` attribute. In a PDF, a Headers list on the cell, naming every header that applies to it. This is what the screen reader reads from when it announces a cell.

<TableTags
  marks={{ autumn: "col", ada: "row", "ada-autumn": "cell" }}
  links={[

    ["ada-autumn", "ada"],

  legend={[
    { kind: "cell", text: "the cell being read" },

  ]}
  lines={tree({ autumn: "col", ada: "row", nine: "cell" })}
  label="The same table with the cell 9 outlined in orange. One arrow goes from it up to the column header Autumn, another left to the row header Ada."
  caption={'The cell "9" (orange) is tied to two headers: "Autumn" above it and "Ada" beside it.'}
/>

So the test for any table is one question per data cell: **which headers does the PDF tie it to?** For the "9" above, the right answer is "Autumn" and "Ada". If the answer is only "Autumn", a listener knows the term and not the student, and the table cannot be followed by ear.

The speech quoted in this post comes from those runs. Each screen reader announces the header that changed: the column header when you move across, the row header when you move up or down. They word it differently, and a quote here joins the pieces one speaks with commas.

## What changed in Typfolio

Typfolio compiles [Typst](https://typst.app) templates to PDF with WebAssembly, in the browser or in Node. It already tagged every PDF and marked the cells inside `table.header(...)` as column headers: the second row of the results above. What Typst cannot work out by itself is which cells name a row, or which header sits under another.

`@typfolio/core` 0.5.0 turns on Typst's in-development `a11y-extras` feature by default. It adds three functions for saying exactly that: `pdf.header-cell`, `pdf.data-cell` and `pdf.table-summary`.

```bash
npm install @typfolio/core@0.5.0 @typfolio/wasm@0.3.0
```

Each example below shows the table with the cell in question marked, then the template and the tags in the PDF. Changed lines are tinted. The tags come from real compiles, read back from the PDF. Under each table is what NVDA says in Acrobat Reader, before and after. JAWS gives the same picture there. Where VoiceOver or another viewer differs, we say so.

> [!NOTE]
> These three functions are still in development in Typst and can be renamed or removed. A template that uses them may need changes when Typfolio's pinned compiler is upgraded.

## The table fixes, in a template

### Say which header sits under which

When one header spans several columns, mark the headers below it with `pdf.header-cell(level: 2)`. The PDF then records that "Autumn" belongs to "Score", instead of tying both to the cell as equals.

With the levels in place, NVDA reads "Score" once, when you reach "Autumn", instead of repeating it on every cell beneath. JAWS shortens the cell in the same way. Two viewers do not follow: VoiceOver with Preview says "Score, Autumn 9" for both versions, and Firefox reads the wrong header for this table with either one ("Spring" for a cell under "Autumn"). Check a table with spanning headers in the viewer your readers use.

If the sub-headers fill a whole row, Typst does this without the new feature: add a second `table.header(level: 2, ...)`. Use `pdf.header-cell` when a cell such as "Student" spans both rows and must stay at the top level.

### Take a non-header out of the header

The corner cell of a table with both kinds of header labels nothing, but inside `table.header` it is still tagged as one. Every row header is then tied to a header with no text. `pdf.data-cell` turns the corner back into an ordinary cell.

## Catching it in your tests

A validator will not tell you a row header is missing, so ask the question yourself. `inspectPdf` from `@typfolio/dev-tools` reads the tags back from the PDF, including each cell's headers. Pick a cell from your sample data and assert what it is tied to:

```ts
import { inspectPdf } from '@typfolio/dev-tools/pdf';

const { bytes } = await compiler.compile(report(sampleData), {
  pdf: { standards: ['ua-1'] },
});
const { structure } = await inspectPdf(bytes);

// Every tag in the document, and the text of each header cell by its id.
const walk = element => [element, ...element.children.flatMap(walk)];
const tags = structure.flatMap(page => page.elements).flatMap(walk);
const text = new Map(tags.filter(tag => tag.id).map(tag => [tag.id, tag.text]));

const cell = tags.find(tag => tag.role === 'TD' && tag.text === '9');
assert.deepEqual(cell.headers.map(id => text.get(id)), ['Autumn', 'Ada']);
```

Against the three files from the top of this post, that assertion fails for the first two and passes for the third. For the first case, a table with no header cells at all, `checkStructure` from the same package reports it without you naming a cell.

`@typfolio/dev-tools` also has a panel that shows these tags beside your page while you work on a template. That is a post of its own.
